| OQ-27 | **`toCEL` string/number confusion produces a silently WRONG boolean on the decision path (found by AUD-S13 / TEST-02).** `toCEL` (`internal/core/aggregate/evaluate.go:182`) binds an integral `json.Number` as int64, a decimal as float64, and anything fitting NEITHER falls back to its **string** form (line 191). When only ONE operand is over-range the compare is cross-type, cel-go reports `no such overload`, `evalLeaf` errors and the engine fails safe — that path is pinned by `TestToCELOverflowFailsSafe` and is fine. **When BOTH operands are over-range they bind as two STRINGS and CEL performs a LEXICAL compare that returns a boolean with NO error**: reproduced, `9e399 > 1e400` evaluates **`true`** where the arithmetic answer is false. For a `new >= old`-shaped non-destructive rule that is a wrongly-PROVEN obligation — an approve-widening fail-open, not a precision complaint. This is the exact failure `internal/evaldecode`'s package doc warns about ("lexically `\"6\" >= \"12\"` is TRUE, so a partition shrink 12->6 would be judged non-destructive and APPROVE. That is the exact forbidden outcome") reappearing at the overflow boundary. **Also a docs-truth defect:** `evaldecode.go:61` already names this "the ADR-0013 residual #1 the S02 evaluator owns" but describes it as toCEL falling back to "float64 (a lossy compare) or its string form" — it does NOT say the string form yields a silently wrong boolean rather than an error, so the residual reads as benign. AUD-S13 deliberately wrote **no** test asserting `9e399 > 1e400 == true`; blessing it would enshrine the fail-open. Candidate fixes: make the string fallback a typed error/sentinel that always errors the leaf (fail-safe, preferred); or reject over-range numerals at the loader/`evaldecode` boundary; or big.Float compare (rejected — reintroduces a decision-path numeric tower). | severity ruling (independent reviewer) → project audit; engine lane after | found by AUD-S13 (PR #35), NOT fixed there (tests-only lane). Leading answer: fail the leaf, never a lexical compare — matches the ADR-0013/GUIDELINES §2 fail-safe direction. Fixing it is a DECISION-PATH change and needs its own fail-safety-reviewed lane |
| OQ-28 | **`builtin/repo-file` enforces PATH containment but not FILESYSTEM containment — a symlink escapes the declared roots (found by AUD-S13 / TEST-06).** `cleanRel`/`cleanRoots`/`underAnyRoot` (`internal/provider/builtin/repo_file.go`) are pure STRING guards: they reject traversal (`../`), absolute anchors, root-escaping and sibling-prefix paths, and `TestRepoFileContainment` pins all of that. They cannot see the filesystem. **`os.DirFS` is explicitly documented in Go as NOT a security boundary**, so a real on-disk symlink under a declared root is followed: reproduced with `topics/evil -> <outside dir>`, `Roots: ["topics"]`, `Anchor: "topics/evil/orders.yaml"` → a **`resolved` fact valued from outside the roots**, directly contradicting the AUD-S13 story's own acceptance criterion ("never a fact from outside the roots"). **Threat context, which is what makes this more than hygiene:** assent evaluates MERGE REQUESTS, so in checkout mode the symlink can arrive **in the very MR under evaluation** — an author adds `topics/evil -> /etc` (or -> another repo path) and a `repo_file` provider then supplies an attacker-chosen fact to the decision engine from outside the declared roots. Path-level and filesystem-level containment are DIFFERENT guarantees and only the former is currently held. Candidate fix: `os.OpenRoot(dir)` + `(*os.Root).FS()` (Go 1.24/1.25, already available on this module's `go 1.25.0`), which refuses symlink traversal out of the root; alternatively `fs.Stat` + `Lstat`-equivalent symlink rejection on every candidate, or resolving and re-containing each candidate before read. Note the fix belongs to whichever FS the host injects, so `RepoFileOpts.FS` may need a documented contract ("must be a symlink-safe root"). | severity ruling (independent reviewer) → project audit; provider lane after | found by AUD-S13 (PR #35), NOT fixed there (tests-only lane).
