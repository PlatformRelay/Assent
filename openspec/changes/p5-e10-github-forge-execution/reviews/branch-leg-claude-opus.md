**Branch review, security and adversarial leg (Opus).** I read the code for every finding below. Where a finding depends on how GitHub behaves, it is marked *believed*: I took it from the GitHub API docs and did not test it against a live API.

SEVERITY: CRITICAL | cmd/assent/run.go:186-295 + internal/forge/github/snapshot.go:`mrPinned` (and gitlab/gitlab.go:572 `mrPinned`) | This branch breaks the REV1-S01 rule that the bytes we judge and the SHAs we pin come from one read. On `main`, the governed file was read with `FileAtRef(..., info.SourceSHA)`, the SHA from the run's own `GetMR`. Now `FileAtBase`/`FileAtHead` go through `mrPinned`. Its cache is never filled by `GetMR`, so it makes a **third, separate** PR read. The record and `DesiredMerge` pin `info.SourceSHA` from read 1, but the judged bytes come from read 3. Attack: head is A at read 1, author pushes B before read 3 (B gets judged), then force-pushes A back. `CurrentHeads` then equals the pin, so approve and `MergeCAS` run on A, which was never evaluated. Today it cannot fire only because every built-in report leaves protected-pipeline-source unknown, so nothing arms. The record already pins a SHA that was not the one judged. No test covers this; a grep for read-chain or pin assertions in the conformance and cmd tests found none. | Make the run's own `GetMR` result the pin: either `GetMR` fills the cache, or `orchestrate` checks after the reads that the adapter's pinned SHAs equal `info` and fails otherwise. Add a conformance case where the head moves between `GetMR` and `FileAtHead`; it must error, or the judged bytes must be at `info.SourceSHA`.

SEVERITY: MAJOR | internal/forge/github/snapshot.go:`mrChangedFiles` | Completeness of the changed-file list relies only on "the last page was short". *Believed:* GitHub's pull-files endpoint returns at most 3000 files and then serves short or empty pages. A PR with more than 3000 files therefore reads as `ChangedFilesComplete=true` with the tail missing. That tail can hold a `.assent/**` path (the attacker controls ordering through filenames that sort before `.assent`). This snapshot is the only `.assent/**` detector when `--checkout` is not set, so the D-042 self-vouch guard sees nothing. The comment says GitHub has "no changes_count equivalent", which is wrong: the PR object carries `changed_files`. Neither `3000` nor `changed_files` appears anywhere in the adapter or the dossier. | Decode `changed_files` from the PR GET and require `entries == changed_files`. Treat `changed_files >= 3000` as incomplete. Add a fixture with more than 3000 files.

SEVERITY: MAJOR | action.yml `bot-author` input + internal/forge/github/auth.go:`Identity` | The marker filter matches on a login string, and `Identity()` just returns the configured `botName`. It is never checked against the forge (no `GET /user` or `GET /app`). With the Actions entrypoint and `GITHUB_TOKEN`, the "token's own login" is `github-actions[bot]`, which every workflow in the repo shares. *Believed:* a same-repo PR author can add a `pull_request` workflow on their branch that posts comments with forged markers as `github-actions[bot]`. Those comments pass `ListBotThreads`/`ListBotNotes` as "ours", so the author can suppress or pre-resolve the bot's BLOCK thread. In v1 GitHub that thread is the only enforcement signal. In practice this is the "any bot" filter the port says must be impossible. | Refuse `github-actions[bot]` as `botAuthor`, or require App or PAT credentials for the action. Resolve the identity from the forge when the client is built and fail if it differs from `--bot-author`.

SEVERITY: MAJOR | cmd/assent/forge_select.go:27-38, docs/usage/cli.md:79 | Remote-host autodetect is not wired in. An empty `--forge` **always** errors; `detectForge`/`detectForgeFromEndpoint` have no caller. `docs/usage/cli.md` and the `selectForge` doc comment both claim autodetect. No `TestForgeSelection` exists and `forge_select_test.go` does not exist, so the REQ-E10-S13-01 verify command (`go test ./cmd/... -run TestForgeSelection`) matches zero tests and passes regardless. Every existing GitLab `assent run` without `--forge`, including against `gitlab.com`, now exits 2. That is an undocumented breaking change for adopters. | Call `detectForge` for the empty case, add `forge_select_test.go` covering unknown host, conflicting signals and the gitlab.com default, and add a CHANGELOG or migration note.

SEVERITY: MAJOR | internal/forge/github/merge.go:`armingRefusal`/`EnablePullRequestAutoMerge` | The GitHub arming deltas (revoke-on-push, dismissal restrictions, merge-result pinning, deferred arming) are only checked inside `EnablePullRequestAutoMerge`, which nothing in production calls. That verb also accepts a report supplied by the caller rather than a probed one. The actual run path (`Reconcile` → `Approve` + `MergeCAS`) is gated only by the three neutral checks in `PreconditionFromReport`. So `TestDeltasFailClosed` passes on a verb that never runs. This also contradicts capability.go's own rule that the gap is computed "AT THE PORT … never by an adapter". | Either move the delta checks into a port-level arming check that `Reconcile` uses, or delete the unreachable verb and mark the deltas as not applicable to immediate merge. Add a test that fails if a capability in an arming set has no production consumer.

SEVERITY: MAJOR | internal/forge/github/write.go:`ResolveThread` + graphql.go:`gqlResolveThread` | `resolveReviewThread` is passed the review **comment's** REST `node_id`. *Believed:* GitHub expects a PullRequestReviewThread id there and will reject a review-comment id, so resolution would fail on the real API. `threadResolutionStates` already fetches the thread `id` and then throws it away. Meanwhile `resolvable-threads` is graded "constant supported" on evidence from the test harness only. That breaks the adapter's own rule that anything unverified is graded unknown. | Map comment `databaseId` to the thread node id from the `reviewThreads` query and resolve by thread id. SEVERITY: MAJOR | internal/forge/github/write.go:`Approve`, merge.go:`gqlEnableAutoMerge` | Neither write verb pins the head. `POST /pulls/{n}/reviews` is sent without `commit_id`. In the gap between `CurrentHeads` and `Approve`, the approval lands on whatever head is current. `MergeCAS` then refuses, but the bot's approval stays on the unevaluated head (unless stale-dismissal is on). `enablePullRequestAutoMerge` omits `expectedHeadOid`; the comment says "the mutation carries no SHA pin", but *believed:* the API does accept one. Neither path is reachable in v1, but both open as soon as a capability is promoted. | Send `commit_id: pinnedSource` with the review and `expectedHeadOid` with the auto-merge mutation, and add a test where the head moves before approval.

SEVERITY: MAJOR | cmd/assent/run.go (`decision.MergeResultGap("gitlab plain-merge …")`) | `cmd/assent` is supposed to be forge-neutral, yet it hard-codes a GitLab-specific gap. Every GitHub DecisionRecord says "gitlab plain-merge exposes no merge-result digest" and sets `mergeResultDigest: null`. At the same time `MergeCAS` pins a real `refs/pull/N/merge` digest. The audit record no longer describes what was enforced, which goes against REQ-E10-S03 (the digest scheme belongs to the adapter). | Take the digest, or the gap and its reason, from the adapter's Snapshot instead of a string in `cmd/assent`.

SEVERITY: MINOR | internal/forge/github/snapshot.go:`ghContentOf` | The Contents API `type` field is ignored, and `encoding: ""` decodes to `[]byte{}`. A symlink or submodule therefore reads as an empty file: invented bytes rather than an error. *Believed:* for a symlink to an in-repo file, GitHub returns the target file's content, so the judged bytes differ from what git stores. | Require `type == "file"` and fail otherwise.

SEVERITY: MINOR | internal/forge/github/github.go:`isRateLimited` | `X-RateLimit-Remaining: 0` on a **200/201** response (the request that used the last unit of quota) is treated as rate-limited and the body is thrown away. A merge or comment that succeeded gets reported as failed, and GETs are retried into a real 403. | Apply the rate-limit check only to 403/429 responses.

SEVERITY: MINOR | action.yml run step | `${{ inputs.subject }}`, `bot-author`, `policy`, `binding` and `pull-request` are pasted straight into the bash `run:` script. That is the standard Actions expression-injection pattern if a caller ever wires a PR-controlled value into one of them. | Pass the inputs through `env:` and quote `"$VAR"` in the script.
